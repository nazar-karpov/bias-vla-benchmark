# Правила работы в этом репозитории

## Ориентация: состояние проекта и карта (сентябрь 2026)

**Измерительная линия ЗАВЕРШЕНА.** Финал: у Magma 4 подтверждённых стереотипных
эффекта по 5–7 мм (пре-регистрированный протокол, 8 сидов, BH), у InternVLA —
ноль при живом гейте. Следующий этап — статья (`docs/PAPER.md`, `icml_paper/`).
Порядок чтения: `README.md` (итог+карта) → `docs/METRICS_ALL_MODELS.md` →
`docs/JOURNAL.md` (записи 2026-08-23…09-03 = финальная линия) → `EXPERIMENTS.md`.

Факты, которые сэкономят день (проверены на практике):

- **Пре-регистрация обязательна** для любого «подтверждения эффекта»: гипотезы,
  объём, тест и правило решения коммитятся ДО запуска (образцы:
  `docs/CONFIRM_CENTER4.md`, `docs/CONFIRM_INTERNVLA_DID.md`; анализ им дословно
  соответствует: `confirm4_analysis.py`, `confirm_did_analysis.py`). Величины
  отобранных по данным эффектов при подтверждении падают ~вдвое (winner's curse).
- **Сид зашит**: `torch.manual_seed(seed)` в `simpler_env/run.py`, дефолт 0 —
  повторный прогон без смены `--seed` повторяет траектории клиентских моделей
  (Magma). У серверных диффузионных (InternVLA) шум серверный и всегда свежий.
  Свежесть шума проверять потраекторно (traj.npz, «0 идентичных из 100»).
- **Single-card центр**: рабочая расстановка `A2A_SINGLE_TILE=1`,
  `A2A_SINGLE_TILE_X=-0.25 A2A_SINGLE_TILE_Y=0.05 A2A_SINGLE_TILE_YAW=90`,
  `BOARD_XY_SCALE=1.0` (масштаб 1.3 уже в model_db кардсетов!). Ровно в центре
  (y=0) рука закрывает лицо на карточке — эффекты исчезают (это был контроль).
- Сторона плитки реально **18.9 см**, а не 14.3: bbox в `model_db.json` занижен
  против меша.
- Анализы single-card: `single_card_assent.py` (для центра — `--card-x/--card-y`;
  мульти-кардсетные семьи ТОЛЬКО через `single_card_center_fdr.py --sets`,
  индексы эпизодов кардсетов пересекаются и затирают друг друга).
- Прогоны живут на H100-ноде cloud.ru в `/workspace/moskalenko/` (переживает
  смену нод; домашняя папка — нет). conda: `/workspace/moskalenko/conda`,
  env `magma_act2answer` (клиент+симулятор), `internvla` (сервер политики).
  `git fetch` на ноде работает только с `protocol.version=1` (закреплён в конфиге).


## Каждый эксперимент — строка в журнале

После **любого** прогона (замер байеса, VLA-eval, sanity, контроль) обязательно:

1. **Добавить строку в `EXPERIMENTS.md`** — таблица «Прогоны»: номер, что за эксперимент,
   скрипт с ключевыми флагами, датасет, модели, объём запросов, ключевой результат
   одной фразой, куда лёг выходной файл.
2. **Пересобрать таблицы метрик:**
   ```bash
   python Act2Answer/scripts/build_metrics_table.py --out-dir ~/bias_benchmark/metrics
   python Act2Answer/scripts/compare_designs.py
   ```
   Они пишут `metrics/metrics_{yesno,choice,comparison}.csv`.
3. **Скопировать CSV в репо и закоммитить** вместе со строкой журнала.

Не оставлять результаты только в чате или в `outputs/*.json` — они там теряются.

## Журнал работы — `docs/JOURNAL.md`

Кроме таблицы прогонов вести **повествовательный** журнал: он нужен для отчёта по проекту,
таблица метрик для этого не годится.

Запись после каждого рабочего блока (не после каждой команды), свежие — сверху:

```
## YYYY-MM-DD — короткий заголовок

**Контекст:** зачем это делали.
**Сделано:** что конкретно, по шагам.
**Результат:** числа и выводы.
**Дальше:** следующий шаг или открытый вопрос.
```

Фиксировать обязательно: **тупики и опровергнутые гипотезы** (что проверяли и почему
отбросили), **найденные проблемы данных**, **смены методики и причину**. Для отчёта это
ценнее итоговых чисел — показывает, почему метод именно такой.

## Метрики: что должно быть в таблице

Для каждого замера фиксировать **все** колонки, а не только итоговое число:

| колонка | зачем |
|---|---|
| `a_pos_pct`, `a_neg_pct` | сырые доли по обеим полярностям — без них не видно механики |
| `S_pp` | эффект в проц. пунктах (0 = байеса нет; содержательно от ~5) |
| `t` | надёжность (>2 — не случайность). **Не путать с величиной**: при n=50 даже 0.7пп даёт t=3 |
| `scenes_S_pos` | в скольких сценах эффект в ту же сторону — проверка устойчивости |
| `n` | число сравнений |
| `pos_bias_left_pct` | позиционный крен модели (50% = нет) |

Обязательно указывать **дизайн подачи** (одна картинка / пара картинок) — эффект
отличается в 5-25 раз, и без этого числа несопоставимы. Для сравнения дизайнов —
`metrics_comparison.csv`.

## Обязательные контроли в замерах байеса

Без них получаются ложные результаты (проверено на практике):

- **негативная полярность** (`boss` + `employee`) — снимает «заметность» картинки.
  Без неё у PaliGemma «босс→чёрные» выглядел надёжным (t=−3.5), а был артефактом.
- **контрбаланс порядка** (ab/ba) в парном дизайне — снимает позиционный крен
  (у PaliGemma он 20пп).
- **проверка валидности** — задать чужой атрибут (`--controls`): если модель отвечает
  одинаково на свой и чужой, замер бессмыслен.
