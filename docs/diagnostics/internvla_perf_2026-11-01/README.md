## Что проверено

- На GPU только наши серверы и клиенты; посторонней нагрузки не обнаружено.
- GPU0 без ECC-ошибок и thermal/power throttling, SM clock ~1980 MHz;
  CPU pressure около нуля, throttled cgroup periods единичны за всё время.
- У всех процессов одинаковые CUDA device/port pairing, checkpoint, OMP/MKL=10.
- До вмешательства GPU0 давала ~416–492 эп./ч за окна 6–24 ч, соседи ~1000.
- Профилирование нового клиента: get_action ~1.05–1.07 с; env.step
  ~0.9–1.0 с; создание Runner ~5–6 с, reset ~7–8 с на шард.
- Привязка всех потоков клиента к удалённой и локальной NUMA не дала
  ускорения: get_action 1.0646 vs 1.0664 с, env.step 0.9909 vs 1.0159 с
  (по 20 шагов). Исходные CPU masks восстановлены; постоянной привязки нет.
- Прямая выборка Python stack через py-spy недоступна из-за ptrace permissions.

## Действие и предел вывода

Дождались CHUNK_STATS s105312 и непустого stats.yaml, остановили только
старого клиента и запустили тот же run_g10_magma.sh, который возобновился

Готовые шарды не удалялись, сервер модели и его RNG не сбрасывались.

**Локализация:** перезапуск клиентского процесса убрал деградацию.
Это согласуется с проблемой долгоживущего клиентского/simulator/CUDA-контекста;
конкретная утечка или внутренняя причина не установлена. Нельзя выдавать
это за доказанную утечку VRAM, неисправность GPU или медленный checkpoint.
NUMA-гипотеза заметного ускорения в короткой пробе не подтвердилась.

Первый запуск профайлера импортировал Runner также в служебном python-скрипте
resume и загрязнил его stdout; новый клиент не стартовал (unbound variable).
Фильтр исправлен на sys.orig_argv: таймеры подключаются только для
`python -m simpler_env.eval`. Повторный запуск продолжился с s105360;
пауза между сохранением s105312 и новым START_G10 составила ~92 с.
